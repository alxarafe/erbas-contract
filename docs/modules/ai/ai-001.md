# AI-001 — Provider-agnostic AI assistant invocation

Status: published in immutable **v0.11.0**, a compatible additive MINOR over
previous published immutable **v0.10.0**. No v0.11.0 backend or client
implementation, adoption, live-provider integration or conformance is claimed.
OpenAPI is authoritative; the single Bruno collection checks the observable HTTP
behavior. This revision does not change CORE-CAP-001 discovery, CORE-CAP-002
invocation or any WMS route.

## Public operation

`POST /api/ai/assistant/invocations` synchronously accepts exactly:

```json
{"message": "List the available units of measure."}
```

`message` is required, nonempty, not whitespace-only, contains no NUL or
unpaired surrogate, and is limited to 4000 Unicode scalar values. The request is
closed: history, conversation IDs, provider/model selection, prompts, tool
definitions, temperature/reasoning settings, identity, permissions, module state
and execution context are not accepted. The caller cannot select an invocation ID.

The closed successful HTTP 200 response is:

```json
{
  "invocationId": "server-generated-ai-invocation-id",
  "answer": "Nonempty answer.",
  "toolsUsed": [
    {"capabilityId": "wms.uoms.list", "invocationId": "server-generated-core-invocation-id"}
  ]
}
```

`invocationId` is server-generated, opaque and nonempty, and is distinct from
every CORE capability invocation ID. `toolsUsed` is always present, may be empty,
preserves successful execution order, and contains only the capability ID and
successful CORE invocation ID. It never contains capability input/output, model
prompts, reasoning, provider requests/responses, token usage or internal execution
metadata. `answer` is nonempty; exact natural-language wording is not contractual.

## Module, permission and processing order

AI is the normal disableable module `erbas.ai`. Its functional permission is
`ai.assistant.invoke`. Administrator/current bootstrap permission registration
may grant it to an administrator; no role-management API or new authorization
model is introduced. Possession of `ai.assistant.invoke` grants no business
capability permission.

Processing order is normative:

1. Authenticate the caller with the existing bearer behavior.
2. Require `ai.assistant.invoke`.
3. Enforce `erbas.ai` availability and enabled state.
4. Validate the request body.
5. Resolve the caller's effective registered READ capabilities using CORE-CAP-001.
6. Expose only those capabilities as tools to the assistant.
7. Treat every model tool request as untrusted input.
8. Re-evaluate module availability and user permissions for each CORE invocation.
9. Invoke through CORE-CAP-002, never through WMS internals or bypassing CORE.
10. Return successful CORE results to the model and produce the final answer.
11. Expose only successful CORE invocation identities in `toolsUsed`.

Authentication precedes permission and module checks. Permission and module
checks precede body validation. A disabled `erbas.ai` returns the existing
`module_disabled` response. A caller without `ai.assistant.invoke` receives 403
`forbidden`. An AI-only authorization does not make WMS or any other business
capability visible.

## Tool catalogue and security

Only effective registered capabilities with `effect: read` are exposed. The
catalogue is derived from the CORE registry and the current user's effective
visibility; it is not a hard-coded WMS list. Future READ capabilities become
available through normal registration without an AI route change. WRITE
capabilities, provider built-in tools, web browsing, code execution, filesystem
tools, external MCP tools and arbitrary remote tools are never exposed.

A user who loses a business permission or whose owning module becomes disabled
between discovery and execution cannot use that capability. CORE-CAP-002 remains
authoritative for masked unauthorized/unavailable/disabled results. The AI
operation must fail safely rather than disclose hidden capability metadata or
retry with elevated privileges. Multiple READ calls may occur in one assistant
invocation; provider-specific parallel tool calling is not required. A finite
server-controlled execution/tool-call budget is required and is not caller state.

WMS is currently the only provider of READ capabilities in this revision. The
contract does not hard-code WMS: the existing `wms.uoms.list`,
`wms.storage-attributes.list` and `wms.item-families.list` descriptors are simply
the currently effective READ catalogue for an appropriately authorized user.

## Grounding

Current ERBAS business state must not be asserted as fact from model knowledge
alone when obtaining it requires an ERBAS capability. The assistant must use a
relevant effective READ capability or state that it cannot obtain the
information. This is server-owned behavior, not a caller-supplied prompt rule.
The contract does not require a particular prompt, model, provider SDK, vector
store or orchestration framework.

## Provider neutrality

Specific providers; model identifiers; API URLs/keys;
temperature, reasoning effort or token settings; raw provider tool-call structures;
and provider-specific error bodies are outside the public contract. A backend may
choose and configure them internally. The public operation must remain identical
across provider and model changes.

## Errors and confidentiality

Every response is strict JSON with `Cache-Control: no-store`; no redirects. Only
HTTP 401 carries `WWW-Authenticate: Bearer`; other responses omit it. Errors use
the closed global ERBAS envelope with exactly one matching detail.

| Status | Top-level and detail code | Condition |
| --- | --- | --- |
| 400 | `invalid_request` | Malformed or structurally invalid body after authorization and module checks. |
| 401 | `unauthorized` | Missing, invalid, expired or disabled-user authentication. |
| 403 | `forbidden` | Authenticated caller lacks `ai.assistant.invoke`. |
| 500 | `assistant_execution_failed` | Malformed provider output, exhausted internal budget or unrecoverable orchestration/tool failure. |
| 503 | `module_disabled` | `erbas.ai` is unavailable or disabled. |
| 503 | `assistant_unavailable` | Temporary assistant/provider unavailability; clients may retry. |

Provider names, upstream URLs/status bodies, API errors, credentials, prompts,
model internals, stack traces, capability input/output and chain-of-thought must
not be exposed. Temporary timeout/rate limit/outage and permanent malformed-output
or orchestration failures are intentionally distinct only at the safe public
level shown above. No `Retry-After` header is introduced.

## Minimum audit

Record the AI invocation ID, authenticated subject, timestamp, outcome, duration,
correlation ID when available, successful tool usage, corresponding CORE
capability invocation IDs and safe failure code. CORE-CAP-002 audit remains
authoritative for each capability invocation. AI audit links the user-level
invocation to successful CORE invocation IDs rather than replacing CORE audit.

Do not log full user messages, prompts, model responses, capability input/output,
credentials or tokens by default. Audit storage, correlation propagation and
logging implementation remain backend-owned; no public audit API or audit fields
are added.

## Scope and acceptance

This revision excludes persistent conversations, history, memory, RAG,
embeddings/vector stores, document ingestion, knowledge stores, WRITE execution,
approvals/confirmations, asynchronous/background/scheduled agents,
capability-to-capability composition, autonomous workflows, MCP, provider built-in
tools, web browsing, code execution, vision, attachments, streaming, voice,
multi-agent orchestration, model routing/fallback, public provider/model selection,
prompt administration and token billing/accounting.

Acceptance includes authentication precedence, AI permission enforcement, module
gate precedence, closed request validation, direct answer with empty `toolsUsed`,
one and multiple successful READ calls, generated and distinct invocation
identities, effective READ-only catalogue filtering, no WRITE/external tools,
per-tool re-evaluation, disabled-module filtering, safe temporary and permanent
failures, no provider/internal leakage, and exact global error envelopes. See
[verification](../../verification/ai-001.md) and
[release notes](../../releases/v0.11.0.md).
