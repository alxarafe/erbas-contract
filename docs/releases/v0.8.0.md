## Compatibility and scope

This is an intentionally **incompatible pre-1.0 MINOR**. Every contractual
legacy error retains its status, headers and technical code, but its closed body
now requires `code` and a nonempty `errors` array. Each legacy detail repeats the
original code. Clients and backends must explicitly adapt before consuming this
revision. Existing successful behavior otherwise remains unchanged.

[API conventions](../api-conventions.md) define the shared methods, statuses,
precedence, atomicity, generic error context, top-level-code roadmap and
[public API versioning policy](../api-conventions.md#public-api-versioning-policy). The code
is required and not deprecated in 0.8.0; intended deprecation starts at 1.0 with
support throughout 1.x, and removal no earlier than 2.0.

[WMS-003](../wms-003.md) adds ItemFamily creation/listing and five association
operations in the existing `erbas.wms` module. It specifies unique pairs without
association IDs, complete attribute representations, Location on creation,
idempotent PUT replacement, strict PATCH pre-state conflicts, DELETE 404 policy,
all-or-nothing changes and staged multi-error diagnostics. It reuses exact UUID,
code/name normalization and COLLECTIONS-001 semantics through neutral field
schemas without weakening existing successful representations.

## Validation evidence

The sole collection contains **494 requests / 2190 named checks**, measured after
implementation; WMS-003 adds 228 requests / 1140 inherited named checks to the
published baseline's 266 requests / 1050 checks. Existing error assertions now
check the canonical envelope. All previous successful requests remain present.

Synthetic runner checks include omission of `errors`, empty `errors`, malformed
details, missing WMS-003 conflict/resource details and partial PATCH/PUT state
changes. Each fault must be reached; partial changes must fail the following GET
assertion. Four ItemFamily catalogue faults cover normalization, scalar length,
persisted normalization and duplicate acceptance. The full positive run measures
actual requests; sequence checks and inherited test discovery measure named
checks. A SHA-256 preservation check reverses only the deliberate error migration
and equivalent field extraction and compares the published v0.7.0 paths/components.

Authoritative `./bin/check` passed in Docker with exit status 0: OpenAPI lint
validated the specification and **130/130 synthetic/unit tests passed**, with
zero failures, cancellations or skips, in **721.644 seconds**. The full positive
run completed all 494 requests; the sole collection measured 2190 named checks.
Owned-runner cleanup succeeded. No external backend was examined; `./bin/test URL`
is necessary for live conformance and was not run for this preparation.

Final scope and documentation review confirmed one shared collection, unversioned
HTTP routes, no backend-specific branching, preserved historical evidence and
the unchanged published v0.7.0 tag. Meaningful new literals were reviewed:
resource/error names and UUID rules use scoped named definitions; pagination
limits reuse the existing fixture configuration; expected request locations and
arbitrary fixture values remain explicit where they improve test independence.
No dependency or lockfile changes are included.

The larger collection uses bounded watchdogs: 120 seconds for full Bruno,
90 seconds for the internal ItemFamily scope, and 900 seconds for the repository
battery. Individual HTTP requests remain limited to two seconds. No retry or
failure suppression is introduced. Direct dependencies, lockfile and Docker base
image remain unchanged.

## Exclusions and release boundary

No Item, per-Item UoM, lots, expiry, dimensions, weights, storage compatibility
rules, locations, zones, topology, inventory, stock, reservations, hierarchy,
inheritance, exclusive groups, family or StorageAttribute update/delete,
fine-grained RBAC, AI, or Java/.NET/Angular implementation is added.

Only erbas-contract is changed. Backend infrastructure remains backend-owned.
No push, PR, merge, tag, release, publication or deployment is authorized by this
preparation. Consumer pins and conformance remain separate approved work.
