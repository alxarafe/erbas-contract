# ERBAS Contract v0.11.0 preparation

**v0.11.0 is an unreleased preparation**, a compatible additive MINOR over
published immutable [v0.10.0](v0.10.0.md). It is not a published release and has
no tag. No consumer change, backend/client adoption, live-provider integration or
live conformance is claimed. Do not publish or tag this revision without the
separately authorized release procedure in [versioning](../common/versioning.md).

## Compatibility and scope

This additive MINOR introduces [AI-001](../modules/ai/ai-001.md):
`POST /api/ai/assistant/invocations`, a provider- and model-agnostic assistant
operation over the caller's effective READ capabilities.

The closed request contains exactly `message`, limited to 4000 Unicode scalar
values and rejecting empty, whitespace-only, NUL and unpaired-surrogate values.
The closed success response contains exactly the server-generated nonempty opaque
AI `invocationId`, a nonempty `answer` and ordered `toolsUsed`. Each successful
tool entry contains only the CORE `capabilityId` and successful CORE
`invocationId`; the AI identifier is distinct from every CORE identifier.

`erbas.ai` is a normal disableable module with functional permission
`ai.assistant.invoke`. Authentication precedes permission and module checks; those
precede body validation. The assistant receives only effective registered READ
capabilities visible to the caller and invokes them through CORE-CAP-002 with
per-tool re-evaluation. AI permission never grants a business permission. WRITE
capabilities and provider built-in, web, code-execution, filesystem, MCP or other
external tools are not exposed.

The contract deliberately excludes provider/model selection, API keys/URLs,
temperature/reasoning settings, raw provider tool structures, history, memory,
RAG, vector stores, ingestion, writes, approvals, asynchronous/autonomous agents,
composition, streaming, vision, attachments, voice, multi-agent orchestration,
routing/fallback and billing. Provider names, model IDs and upstream errors are
not part of the HTTP contract.

Safe failures reuse the global error envelope: `invalid_request` (400),
`unauthorized` (401), `forbidden` (403), `assistant_execution_failed` (500),
`module_disabled` (503) and retryable `assistant_unavailable` (503). All responses
are strict JSON with `Cache-Control: no-store`; only 401 carries
`WWW-Authenticate: Bearer`. Provider/internal details, prompts, reasoning and
capability payloads are never exposed. CORE-CAP-002 audit remains authoritative;
AI audit links successful CORE invocation IDs without logging full payloads by
default.

Published v0.10.0 CORE, authentication, user, module, collection, capability and
WMS behavior remain unchanged. The common error envelope is unchanged. Historical
release notes and verification reports remain unchanged.

## Focused verification

The single collection now contains **590 requests / 2587 named checks**:
**30 requests / 120 named checks added**. All 560 existing requests and their
assertions remain intact. New AI scenarios cover authentication and permission
precedence, AI module disable/restore, closed request validation, direct answer,
one and multiple READ calls, unique and distinct identities, module filtering and
restoration, and the safe error envelope. Synthetic AI tests additionally cover
temporary/permanent failures, per-tool module re-evaluation, assistant-only
authorization without business permissions, and runner rejection of provenance
defects.

The fully dereferenced contract preserves the immutable v0.10.0, v0.9.0 and v0.8.0
definitions when AI-001 is removed.

See [AI-001 verification](../verification/ai-001.md) for commands, results and
limitations. Synthetic fixtures verify the runner; they do not establish backend
conformance, real model behavior, trusted runtime context propagation, provider
integration, actual audit implementation or live conformance.

## Adoption prerequisites and limitations

Full live conformance requires an AVAILABLE enabled `erbas.ai` module, an
administrator granted `ai.assistant.invoke`, the existing disposable CORE/WMS
prerequisites, and a backend-owned deterministic conformance assistant/model
adapter for the shared success scenarios. It must not require a live external LLM
service, API key, internet provider access or probabilistic output during normal
contract validation. No backend is modified by this contract task.
