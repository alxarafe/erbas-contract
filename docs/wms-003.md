# WMS-003: Item Families and Storage Attribute associations

This is **unpublished v0.8.0 preparation**, based on published immutable v0.7.0
at `76618b4d6776dca5e13466e7fde44af675d5b08f`. No backend/client v0.8.0
adoption or conformance is claimed. OpenAPI defines behavior; the sole Bruno
collection checks it. Follow [API conventions](api-conventions.md) and
[COLLECTIONS-001](collections.md). v0.8.0 is an intentionally incompatible
pre-1.0 MINOR because every legacy error now requires `errors` as well as `code`.
Other existing successful behavior remains unchanged.

## Scope and model

ItemFamily is a closed `{id, code, name}` catalogue resource under the existing
`erbas.wms` dynamic module. POST accepts exactly `{code, name}`. No associations
are embedded in family catalogue responses.

`id` reuses WMS-001/WMS-002: server-generated, non-nil canonical lowercase UUID,
version unspecified, opaque to consumers. Path IDs use the same lexical rules;
malformed IDs are 400, well-formed absent IDs are 404.

`code` matches `^[A-Z][A-Z0-9_]{0,29}$`: 1..30 ASCII characters, initial A-Z,
then A-Z, digits or underscore. No trimming, uppercasing or Unicode normalization.
Uniqueness is exact and case-sensitive within the family catalogue; `IS_*` is
syntactically valid. The same code may exist in a different catalogue.

For `name`, remove boundary U+0020, U+0009, U+000A and U+000D only. Preserve
all other Unicode spaces, internal whitespace and case. After normalization,
require 1..255 Unicode scalar values. Reject NUL and unpaired surrogates.
Persist and return the normalized value. Raw padding does not count toward the
limit. Neutral catalogue field schemas reuse these exact WMS-002 semantics.

The many-to-many relation has the unique contractual identity
`(itemFamilyId, storageAttributeId)`. There is no association UUID. Persistence
structure, transaction mechanisms and migrations remain backend-owned.

## Operations

| Method and path | Behavior |
| --- | --- |
| POST `/api/wms/item-families` | Create a family, 201 with complete persisted representation. Exact duplicate code: 409 `wms_item_family_code_conflict`. |
| GET `/api/wms/item-families` | Paged family catalogue without associations. |
| GET `/api/wms/item-families/{familyId}/storage-attributes` | Paged complete StorageAttribute objects `{id, code, name}`; no duplicated family ID. Missing family: 404. |
| POST `/api/wms/item-families/{familyId}/storage-attributes` | Create exactly one pair from closed `{storageAttributeId}`. 201 with closed `{itemFamilyId, storageAttribute:{id,code,name}}`. |
| PUT `/api/wms/item-families/{familyId}/storage-attributes` | Closed `{storageAttributeIds:[UUID...]}` replaces the entire set atomically. 204 without a body, including identical sets. Empty array removes all. |
| PATCH `/api/wms/item-families/{familyId}/storage-attributes` | Closed optional `add`/`remove` UUID arrays, at least one nonempty. Strict pre-state evaluation, atomic 204 without a body. |
| DELETE `/api/wms/item-families/{familyId}/storage-attributes/{storageAttributeId}` | Remove one pair, 204 without a body. Repetition normally returns 404 and remains HTTP-idempotent. |

Association POST requires `Location` exactly
`/api/wms/item-families/{familyId}/storage-attributes/{storageAttributeId}`.
It identifies the created pair even though individual GET is not provided.
Existing pair: 409 top-level `wms_item_family_storage_attribute_conflict`, detail
`wms_item_family_storage_attribute_already_exists`. Failures change nothing.

All JSON objects are closed; duplicate field names, wrong types, nulls,
malformed JSON and non-object roots are structural 400 `invalid_request`.
Mutations accept no query parameters. PUT/PATCH reject duplicate UUIDs within
an array with 400. No delete-all endpoint is necessary: use PUT with `[]`.

## Strict PATCH and atomicity

Validate every referenced master before checking relation state. Evaluate all
adds and removes against the original state, never a partially modified set.
Adding an existing pair conflicts; removing an unassociated attribute conflicts.
An empty/no-op PATCH is invalid. The same ID once in each array is structurally
valid: if initially associated, add conflicts; otherwise remove conflicts. If
the master does not exist, 404 wins. Report every determinable conflict against
that original state; any conflict rejects the whole operation.

POST, PUT, PATCH and DELETE have observable all-or-nothing behavior. Failed
PUT/PATCH, including resource validation failures, must preserve the exact
original set. Success is visible in subsequent reads. No backend transaction
implementation is prescribed.

## Error stages and context

Authentication → administrator authorization → WMS gate → structure (400) →
referenced-resource existence (404) → relation state (409) → mutation.
Return all safely determinable details within the selected stage, never mixed
404 and 409 diagnostics. A missing family does not prevent reporting other
missing masters at the same existence stage when safely determinable.

| Condition | Detail code |
| --- | --- |
| Missing family | `wms_item_family_not_found` |
| Missing master StorageAttribute | `wms_storage_attribute_not_found` |
| Both masters exist, pair absent on DELETE | `wms_item_family_storage_attribute_not_found` |
| PATCH add already associated | `wms_item_family_storage_attribute_already_exists` |
| PATCH remove not associated | `wms_item_family_storage_attribute_not_associated` |

A single missing reference uses its detail code at top level. Multiple missing
references use top-level `wms_item_family_storage_attributes_not_found`.
PATCH conflicts always use top-level
`wms_item_family_storage_attributes_conflict`.

Useful context uses `resource` names `wms_item_family`, `wms_storage_attribute`,
`wms_item_family_storage_attribute` and opaque `resourceId`. A missing relation
uses the path attribute ID as context; the requested family is already in the
URL. Referenced master body locations use `/storageAttributeId`,
`/storageAttributeIds/N`, `/add/N`, `/remove/N` as appropriate. PATCH conflict
details require attribute context and the exact operation path.

For deterministic diagnostics, emit missing family first, then references in
body array order, add before remove. Repeated references across add/remove retain
both request locations. For example, a missing ID appearing in both arrays
produces two missing-reference details; no later relation conflicts are added.

```json
{
  "code": "wms_item_family_storage_attributes_conflict",
  "errors": [
    {"code":"wms_item_family_storage_attribute_already_exists","resource":"wms_storage_attribute","resourceId":"<uuid-A>","path":"/add/0"},
    {"code":"wms_item_family_storage_attribute_not_associated","resource":"wms_storage_attribute","resourceId":"<uuid-B>","path":"/remove/0"}
  ]
}
```

## Security, pagination and localization

Every operation requires bearer authentication, administrator authorization and
enabled `erbas.wms`. Anonymous malformed requests return 401, non-admin requests
403, disabled-WMS admin requests 503, then structural errors 400. The gate affects
all seven operations immediately; disable/re-enable preserves catalogues and
relations. No new module or fine-grained RBAC is introduced. All responses have
`Cache-Control: no-store`; only 401 has `WWW-Authenticate: Bearer`. No redirects.
Technical fields, errors and stored user content are Accept-Language invariant.

All three GET collections follow COLLECTIONS-001: offset default 0, limit
default 50, limit 1..100, each at most once, strict decimal integer text. Reject
unknown parameters, empty, whitespace, exponent and fractional forms. Ordinal
code ASC sorting happens before slicing, total counts the complete set, and
huge/beyond-total offsets return 200 with empty items and complete metadata.
No filter, search, configurable sorting or cursor is added.

## Java/.NET portability review

The recorded [WMS-002 review](wms-002.md#java-net-portability-review) establishes
the shared catalogue foundation and the explicit Unicode rules. The new family
catalogue requires equivalent observable behavior with independent uniqueness.
The [laboratory findings](wms-002.md#laboratory-evidence-and-selection) motivate
the pair relation, without adopting laboratory persistence or routes.

Both Java and .NET can implement unique pairs, reference validation and atomic
set changes using their own persistence facilities. Each can read the original
set, validate references before conflicts, collect deterministic diagnostics,
and commit the desired set atomically. Concurrency must preserve these observable
outcomes; locks, isolation and transaction choices remain implementation-owned.
Explicit projections produce complete attribute representations and ordinal
ordering. Shared authorization and module gates apply before deserialization.

A single POST creates a pair, PUT expresses idempotent desired state and PATCH
provides strict changes with diagnostics. These semantics are equally testable
on both stacks through subsequent reads and deliberately rejected batches.
Generic error context avoids binding the contract to framework validation
objects, exception classes or database names. Framework-localized messages do
not become wire requirements. Neither stack must copy the other's internals;
no backend source or live service was inspected in this task.

## Conformance and exclusions

The single shared collection covers the complete catalogue boundary matrix,
security precedence, strict pagination, language invariance, association state,
all mutation forms, multi-errors and post-failure persisted-state checks.
Synthetic faults prove missing/empty/malformed error details, omitted multi-error
details and partial PUT/PATCH changes are detected. See
[release preparation](releases/v0.8.0.md) for measured counts and validation.
A disposable initially empty family catalogue is required, in addition to the
existing suite prerequisites. Tests create master attributes and leave data
for the backend-owned environment to dispose of.

Excluded: Item, per-Item UoM, lots, expiry, dimensions, weights, compatibility
rules, locations, zones, warehouse topology, inventory, stock, reservations,
hierarchy/inheritance, exclusive attribute groups, family update/delete,
StorageAttribute update/delete, fine-grained RBAC, AI and Java/.NET/Angular
implementation. No push, PR, merge, tag, release, publication or deployment is
part of this preparation.
