# WMS-001: first business vertical

Current v0.8.0 preparation follows [API conventions](api-conventions.md), including
the required `code` + nonempty `errors` error envelope. Statuses and technical
codes below retain their meaning. Published immutable baseline is v0.7.0.
No v0.8.0 consumer adoption or conformance is claimed.

## Status and authority

WMS-001 is part of published immutable **v0.6.0**, target
`92d1282154f340aadcfdf93f52a82a1f3472b335`, adopted by Java and .NET.
OpenAPI specifies HTTP behavior; the single Bruno collection verifies it.
Published v0.7.0 adds [WMS-002](wms-002.md). Unpublished v0.8.0 adds

uses `REQUIRES`/`FORBIDS`, whereas v2 models `REQUIRE_LOCATION`/`SEPARATE`.
These are concrete reasons to reconcile operations before promoting that domain.

## Vertical selection

| Alternative | Dependencies / value | Contract, migrations and portability | Decision |
| --- | --- | --- | --- |
| UoM only | No other aggregate. Real master data for future Item quantities. | One small persisted catalogue, two operations; portable admin policy; exercises business-module runtime. Low premature-decision risk. | Selected. |
| UoM + ItemFamily | Family attributes/hierarchy open additional choices. | Adds aggregate, links, reference errors and storage catalogue or removes existing family meaning. Portable, but unnecessarily broad. | Defer. |
| UoM + Item | Existing Item requires family and base UoM. | Adds SKU uniqueness, family lookup, lot/expiry invariants and more migrations/security scenarios. Making family optional merely to avoid its design would degrade evidence. | Defer. |
| Minimal Warehouse | Useful physical identity. | Either a thin name/code catalogue with limited runtime value, or formatting/topology/policy decisions. Does not establish Item quantities. | Defer. |
| Storage attributes / HU / operations | Supports future AI operational queries. | Requires rule/topology/stock decisions not settled across the lab's two models. | Defer. |

Every alternative is implementable on both stacks. None needs future AI. UoM
offers the smallest useful application boundary for AI to consume later; this
increment introduces no tools, capabilities, bus or cross-module calls.

## Deliberate UoM decisions

| Laboratory rule | ERBAS decision and reason |
| --- | --- |
| `code` required, 2–10 uppercase alphanumeric | Required, **1–10**, `^[A-Z][A-Z0-9]{0,9}$`. A local mnemonic such as `M` is valid. Uppercase avoids aliases without hidden normalization; these are catalogue codes, not case-sensitive SI symbols or a claim of UNECE compliance. |
| `description`, maximum 255 | Retain the property: a display description, not another identifier. Required string, trimmed before validation and persistence; 1–255 Unicode scalar values after trimming. Empty/whitespace-only values, NUL and unpaired surrogates are invalid. Preserve case and internal spaces. No language-specific stored copies. |
| Unique code | Retain exact catalogue-wide uniqueness, enforced atomically. A preflight lookup alone must not allow concurrent duplicates. No family/warehouse scoping. |
| Server UUID v7 | Retain server UUID identity, canonical lowercase non-nil text; **do not prescribe version**. v7 has useful storage locality but is not needed by clients, ordering or this domain. v4/v7 are possible implementation choices; no dependency introduced to force v7. |
| POST + collection GET | Retain only these operations. Persisted IDs support future references. No update/delete, GET by ID/code, conversion, dimension or standardized unit catalogue without a confirmed use case. |
| Bare unpaged array | Replace with existing COLLECTIONS-001 envelope and limits. Even a small catalogue should use the established client convention; no second unbounded-list convention. |
| Code ASC | Retain and define ordinal ASCII comparison, before slicing. Unique codes remove ties. No configurable sorting/filtering. |
| `/api/uoms` | Use **`/api/wms/uoms`**. Flat routes make UoM look Core-owned. The namespace preserves WMS ownership and future `/api/wms/items`, `/warehouses`, `/inventory` consistency, without prescribing those future APIs. |
| English literal error strings | Do not copy. Common WMS errors are closed technical codes; backend exceptions must not leak messages or SQL details. |

These are ERBAS design decisions made within the approved WMS-001 scope, not
claims that the laboratory or a logistics standard already mandates them.
UUID ordering/locality and opaque client use were reviewed against
[RFC 9562](https://www.rfc-editor.org/rfc/rfc9562.html#section-6.11); no UUID
version becomes an observable WMS requirement.

### WMS-001A: description normalization and exact code syntax

Trim removes every consecutive ASCII space (U+0020), tab (U+0009), CR (U+000D)
and LF (U+000A) from each end, reusing this contract's existing whitespace
convention. It does not prescribe a framework string method. Other characters,
case and internal whitespace remain unchanged. Validate the resulting value's
**1..255 Unicode scalar values**, persist it, and return it on creation and listing.
Padding is not counted toward the length limit. `description` remains user
content, never a localized runtime message.

| Input description | Result |
| --- | --- |
| `Standard Box` | `Standard Box` |
| ` Standard Box ` | `Standard Box` |
| `   BOX   ` | `BOX` |
| `Standard   Box` | `Standard   Box` |
| Empty string or three spaces | 400 `invalid_request` |
| 256 scalar values after trimming | 400 `invalid_request` |

The exact code regex is `^[A-Z][A-Z0-9]{0,9}$`: 1..10 ASCII characters, first
an uppercase letter, then uppercase letters/digits. `A`, `EA`, `BOX`, `PAL`,
`KG`, `A1` and `BOX10` are valid. `1`, `1A`, `box`, `Box`, `_A`, `A-B`, `A_B`
and `ABCDEFGHIJK` are invalid. Codes are neither trimmed nor uppercased.

OpenAPI separates raw description input from normalized output: the latter has
minLength 1/maxLength 255; the input has no raw maximum because padding is allowed.
The normalization order and normalized length are normative prose and executable
Bruno assertions, not proprietary schema extensions.

## Module, security and gating

`erbas.wms` is AVAILABLE when the application's composition includes WMS. Its
descriptor uses the supported Module API (currently 1), with no dependencies.
Existing `/api/modules` exposes the unchanged closed Module representation;
there is no new display name, source or development-only field. Canonical
`erbas.dev.math`/`erbas.dev.statistics` stay validation-only and are not WMS
dependencies. Synchronization initializes a new WMS state enabled through the
normal runtime policy; retained state remains authoritative across restarts.

Both UoM operations initially require an enabled bearer-authenticated
**administrator**. Evaluation order is authentication (401), admin authorization
(403), dynamic persisted module gate (503), then parsing/validation/operation
(400/409/success). Invalid bodies/query inputs must not mask 401/403/503. Disabled
WMS never prevents CORE module administration or recovery. Disable/re-enable is
effective on successive requests without restart and preserves UoM data.

Administrator-only catalogue maintenance is the initial portable policy, using
existing Java administrative authorization and .NET CoreAdmin. Fine-grained WMS
read/write permissions are desirable later, but require a separately reviewed
contract evolution: no Java RBAC infrastructure or invented permission claims
are required for this vertical.

## HTTP contract

`POST /api/wms/uoms` accepts exactly:

```json
{"code":"EA","description":"Each"}
```

201 returns exactly `{id, code, description}`. Property names are case-sensitive;
missing, null, wrong-type, extra or duplicate properties, malformed JSON and
non-object roots give 400. POST accepts no query parameters. Creation is committed
before success. Duplicate code returns 409 and leaves the original record intact.
No `Location` header is required without a resource GET route.

`GET /api/wms/uoms` accepts only optional `offset` and `limit`, each once, as
base-10 integer text. Defaults: 0/50; offset nonnegative; limit 1–100. Empty,
fractional, exponent, whitespace, repeated or unknown query input gives 400.
Ordering is code ASC before pagination; total is before slicing. At/beyond total
returns 200 with empty items, not 404.

```json
{"items":[],"offset":0,"limit":50,"total":0,"order":[{"field":"code","direction":"asc"}]}
```

| Status | Exact error body / meaning |
| --- | --- |
| 400 | `{"code":"invalid_request","errors":[{"code":"invalid_request"}]}` — invalid WMS body/query; no mutation. |
| 401 | `{"code":"unauthorized","errors":[{"code":"unauthorized"}]}` — no valid enabled bearer. |
| 403 | `{"code":"forbidden","errors":[{"code":"forbidden"}]}` — authenticated non-admin. |
| 409 | `{"code":"wms_uom_code_conflict","errors":[{"code":"wms_uom_code_conflict"}]}` — exact code exists; no mutation. |
| 503 | `{"code":"module_disabled","errors":[{"code":"module_disabled"}]}` — WMS administratively disabled. |

All WMS responses use `application/json`, `Cache-Control: no-store`, no redirects.
Only 401 includes `WWW-Authenticate: Bearer`; other statuses omit it. Disabled
responses omit Retry-After. Unexpected infrastructure errors must not be
misclassified as validation, duplicates or disabled-module errors.

## i18n and application ownership

There are **no generated human messages** in this common wire shape. Error
codes/properties/IDs are language-independent. `description` is user content,
not a runtime message: Accept-Language must not translate or change it. Bruno
checks equal duplicate errors with `en`/`es` and unchanged persisted text with
`es-ES`; it does not claim to test message negotiation where no human text exists.

Any WMS-owned human text introduced within a later approved representation must
use WMS resources, English base/fallback and Spanish through standard request
Accept-Language negotiation. Java bundles live with WMS under an explicit
`i18n/wms/messages` basename; .NET uses a WMS assembly marker and neutral/Spanish
`.resx`. Domain/Application express typed codes/data, never translated strings
or framework localizers. Existing Core/Identity resources remain Core/Identity.
No global Java/.NET error-envelope reform is included.

## Future compatibility and implementation feasibility

UoM is separate from User/Identity, family, warehouse and physical HU. Immutable
UUIDs can be referenced by future Item base UoM and item-specific conversions.
`BOX`/`PAL` do not imply global conversion factors or physical HU types. Item's
family relationship and `isExpirable => isBatchManaged` remain future design
constraints to review; no field or behavior for them is added now.

Batch/expiry, inventory, HU, receipts/issues and relocation need separate verticals
and reconciliation of the laboratory's operational models. Their public WMS
Application use cases can later serve AI queries/actions with inherited user
authorization. AI must never access EF/JDBC/PostgreSQL, tables or private
repositories directly. WMS has no AI dependency.

Portability was checked against current backend `docs/modularity.md`, runtime
gates, module sources, admin security and I18N-001 configuration. Spring can use
the existing module source/annotation/interceptor, Jakarta Validation and JDBC
transactions/Flyway. ASP.NET Core can use ModuleBuilder/IModuleSource/IHttpModule,
the endpoint filter, CoreAdmin and EF migrations/transactions. Unicode scalar
length must be checked explicitly (Java codePointCount, .NET Rune enumeration),
instead of assuming native string length matches the contract. Closed-body and
duplicate-key validation belongs at HTTP; code/uniqueness invariants belong in
domain/application and persistence. Constraint names and database technology
are not contract requirements. No new runtime infrastructure is necessary.

## Executable conformance and prerequisites

Full v0.6.0 conformance requires disposable enabled admin credentials,
the two existing canonical dev descriptors and **enabled AVAILABLE `erbas.wms`
with an initially empty UoM catalogue**. Additional AVAILABLE modules are allowed.
Backends own migration, initialization, readiness and cleanup; the shared runner
never accesses SQL or seeds business state internally.

The 52-request WMS sequence is appended to the unchanged 130 existing definitions.
It tests empty/default listing, 401/403 precedence, module disable/re-enable,
503 precedence, maximum code/Unicode-description lengths, one-character code,
reverse creation versus ordinal listing, duplicate rejection without update,
ordered windows/beyond total, invalid query/body variants, language-independent
errors and persistence through disable/re-enable. Successful execution leaves
WMS and the canonical dev modules enabled, four UoMs persisted, and test users;
dispose of the environment even after success. After failure, discard it.

WMS-001A also verifies padded descriptions at normalized lengths 1 and 255,
rejection above 255, empty/space-only input, preservation of internal spaces,
and normalized values in subsequent GET requests. Code negatives include numeric
first characters, separators and boundary spaces. The unchanged one-character
and ten-character code cases remain valid.

Synthetic HTTP fixtures model only this observable contract. WMS fault runs reuse
the same definitions with the existing scope mechanism and contractual user/login
bootstrap. They must reach their configured defect and prove the shared suite
rejects it, rather than passing on an unrelated bootstrap failure. No backend
conformance is claimed by repository `bin/check`.
