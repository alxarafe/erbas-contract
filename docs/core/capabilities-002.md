# CORE-CAP-002 — Synchronous READ capability invocation

Status: approved contract-only preparation for **unpublished v0.10.0**, a
compatible additive MINOR over published immutable **v0.9.0**. No backend/client
implementation, adoption or live conformance is claimed. OpenAPI is authoritative;
the existing single Bruno collection checks the observable HTTP behavior.
[CORE-CAP-001](capabilities-001.md) discovery, registration, descriptors, versions,
visibility and the current administrator permission mapping remain unchanged.

## Public operation and processing order

`POST /api/core/capabilities/{capabilityId}/invocations` executes synchronously.
The closed request is exactly `{"input": {...}}`; `input` is required and must
conform to the effective descriptor's `inputSchema`. It is structured JSON,
not query-string text. The closed successful HTTP 200 response is:

```json
{
  "invocationId": "server-generated-opaque-identifier",
  "capabilityId": "wms.uoms.list",
  "output": {"items": [], "offset": 0, "limit": 50, "total": 0,
             "order": [{"field": "code", "direction": "asc"}]}
}
```

The server generates a nonempty opaque invocation identifier. The capability ID
exactly matches the requested ID; no normalization or aliasing is introduced.
`output` must conform to the resolved descriptor's `outputSchema`. The generic
CORE response schema describes the envelope; the descriptor reference determines
the provider-owned output constraints. No backend runtime JSON Schema validation
mechanism is prescribed. Known non-contractual output must never be emitted as
successful HTTP 200.

Processing order is normative:

1. Authenticate using the existing bearer behavior.
2. Validate capability ID syntax using the existing CORE-CAP-001 rules.
3. Resolve the effective registered capability using the discovery visibility rules.
4. Enforce owning module availability/enabled state and all required permissions.
5. Only then validate the invocation body and descriptor input.
6. Execute the registered READ provider capability.
7. Return its contractual output in the invocation envelope.

Discovery is not an authorization token: each invocation reevaluates trusted
current module/user policy. Hidden entries remain indistinguishable even with
malformed JSON or invalid input. `requiredPermissions` are authorization
requirements, never grants. For the existing WMS permissions, an enabled
administrator has all three; a normal user has none. No role or permission
management is introduced.

## Existing provider behavior

| Registered READ capability | Input | Output |
| --- | --- | --- |
| `wms.uoms.list` | `CapabilityListInput` | `WmsUomCollection` |
| `wms.storage-attributes.list` | `CapabilityListInput` | `WmsStorageAttributeCollection` |
| `wms.item-families.list` | `CapabilityListInput` | `WmsItemFamilyCollection` |

The existing normative [WMS declarations](../../openapi/modules/wms/capabilities.json)
remain byte-identical. Capability behavioral versions remain `1.0.0`.
Optional integer `offset`/`limit` preserve existing defaults, bounds, totals,
ordering and offset-at/beyond-total behavior through the referenced common
pagination and complete collection schemas. No new WMS business behavior exists.

CORE owns resolution, authentication/authorization, invocation governance and the
public envelope. The provider owns its business/data behavior. Dispatch may be
in-process to a registered handler or application service; internal HTTP loopback
is not required. Backend-owned idiomatic registration/dispatch remain free to
differ between Java and .NET. The architecture is already approved; this task
neither inspects other repositories nor claims existing backend support.

## Trusted execution context

Execution conceptually carries `invocationId`, `correlationId` when available,
authenticated subject/user identity, `capabilityId`, owning module, effective
permissions and `caller = user`. These are trusted server-side semantics only,
not public HTTP fields or language-specific classes.

All security-sensitive values come from authenticated server state and the
effective registry/policy. The request must not supply identity, permissions,
roles, scopes, module state or execution context. The outer request is closed;
the existing list input is also closed and accepts only `offset` and `limit`.
The success-only public `invocationId` is generated by the server; input cannot
set it. Required permissions do not expand the caller's effective permissions.

## Errors and confidentiality

Every response is strict JSON with `Cache-Control: no-store`. No redirects.
Only HTTP 401 carries `WWW-Authenticate: Bearer`; other responses omit it.
Errors use the existing closed global ERBAS envelope with exactly one matching
detail for this operation:

| Status | Top-level and detail code | Condition |
| --- | --- | --- |
| 400 | `invalid_request` | Invalid ID syntax, or invalid body/input after effective authorization. |
| 401 | `unauthorized` | Missing/invalid/expired/disabled-user authentication, before validation. |
| 404 | `capability_not_found` | Syntactically valid unknown, unavailable, disabled or unauthorized capability. |
| 500 | `capability_execution_failed` | Any unexpected provider/execution reason that prevents valid contractual output. |

```json
{"code":"capability_execution_failed","errors":[{"code":"capability_execution_failed"}]}
```

Provider exceptions and output-contract violations have the same public failure.
Do not expose implementation details or additional execution-error codes. Internal
`invocationId` remains available for auditing failed attempts, but is absent from
the public error envelope. Pre-execution masked 404s retain discovery semantics;
they are not execution failures. Existing direct WMS routes retain their errors,
including their existing disabled-module 503 response.

## Minimum audit

Record invocation attempts/results with invocation ID, correlation ID when
available, capability ID, owning module, authenticated subject, timestamp,
outcome (`completed`, `denied`, `failed`), duration and safe error code when
applicable. Preserve an internal invocation ID for failed attempts as well as
successful ones. For rejected attempts where identity or module cannot be
resolved, record their unavailability without inventing authenticated identity
or resolving hidden metadata for the caller. Audit stays server-side; no public
audit API or public error fields are added.

Do not log full input or output by default. Audit must not require payloads,
credentials or sensitive implementation details. Storage, runtime context types
and logging implementation are backend responsibilities.

## Scope and acceptance

This revision executes READ capabilities only. It does not define write execution,
capability-to-capability delegation/composition, confused-deputy/delegation
solutions, DataScope, disclosure policies, approvals, asynchronous jobs, retries,
remote capabilities, workflows, AI/LLM/RAG/MCP behavior, roles, permission-management
APIs or new WMS capabilities. Descriptor `write` classification remains unchanged;
write invocation behavior is outside this revision.

Acceptance includes authentication precedence, success for all three declared
reads, exact capability identity, generated nonempty invocation identity,
structured/default pagination, malformed IDs/bodies/inputs, masked unknown,
unauthorized/unavailable/disabled providers, rejection of caller security context,
and output equivalence with existing provider collection shapes and data.
See [verification](../verification/core-cap-002.md) and
[release preparation](../releases/v0.10.0.md). Synthetic fixtures verify the runner;
backend execution, trusted context and audit require backend-owned verification.
